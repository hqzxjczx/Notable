一、执行摘要

本报告综合四轮独立 deep-research，覆盖四个持续演进的开源 AI agent 项目。核心图景：它们处于不同的抽象层——Hermes 与 OpenClaw 是自包含 agent harness（带记忆、平台网关、自主执行），OpenHuman 是本地优先的多 agent 编排器（可指挥其他 harness），holaOS 则是工作区管理层（位于 Claude Code/Codex 等执行器之上）。三者并不直接同层竞争。

Hermes OpenClaw OpenHuman holaOS

Hermes Agent：Nous Research 出品的"自改进自主 agent"，最佳实践集中于四条——自动注入 AGENTS.md、稳定系统提示词保缓存、有界冻结快照记忆（MEMORY.md/USER.md）+ 可选 mem0、容器后端跑不可信代码。20+ 消息平台，官方《Migrate from OpenClaw》指南，是 OpenClaw 的直接替代目标。

OpenClaw：作为对比基线，多平台个人 AI 助手，记忆/技能/编排体系成熟；Hermes 提供 hermes claw migrate 直接导入其配置。

OpenHuman（GPL-3.0，~36k stars，早期 beta）：本地优先 agent 编排器，每个 agent 回合都跑在 tinyagents 2.1 图引擎上（检查点/暂停/恢复），Memory Tree 确定性桶密封管道存本地 SQLite + Obsidian vault，Signal 协议端到端加密的 A2A 编排，20 分钟自动抓取循环。注意：其"单循环"对 Hermes 的概括与 Hermes 自己的"内置学习循环"自述冲突。

holaOS（Modified Apache 2.0，~5.5k stars）：本地优先 TypeScript/Electron 桌面应用，同一工作区并排跑 Claude Code / Codex / 自研 agent，共享文件系统 markdown 记忆与 MCP 工具。把自己定位在执行器之上的工作区层，竞争 agent SDK 而非执行器。⚠️ 它与前三者的直接对比 claims 未通过验证。

三、Hermes Agent

3.1 四条最佳实践（首轮研究，全部 3-0 高置信）

BP1上下文文件自动注入 3-0

  • 会话启动自动注入 CWD 顶层 AGENTS.md；子目录文件惰性发现进工具结果（非系统提示词），避免缓存膨胀。
  • 优先级：.hermes.md > AGENTS.md > CLAUDE.md > .cursorrules（首个命中胜出）。
  • 源码：agent/subdirectory_hints.py（向上查 5 层）、agent/prompt_builder.py。

BP2提示词缓存经济学 3-0

  • 缓存按模型 + 账户键控；/model 切换、provider fallback、凭据轮换都会迫使下轮全价重读。
  • "偶尔切换没事；长会话里频繁切换成本成倍。"（tips.md 原文）
  • 业界佐证：LangChain PR #33850、OpenClaw PR #53212（拆静态/动态块保缓存）。

BP3有界冻结快照记忆 3-0

  • MEMORY.md（~2,200 字符）记录环境事实/约定/学到的经验；USER.md（~1,375 字符）记录用户画像。
  • 会话开始冻结快照注入系统提示词；写入立即落盘但不改提示词，下个会话才可见。
  • 外置 provider 同时最多一个，与内置叠加（mem0 三模式四工具）。

BP4容器后端安全边界 3-0

  • 危险命令检查（递归删除/SQL drop/curl 管道 shell）在容器后端跳过——容器即边界。
  • 不可信代码最佳实践：TERMINAL_ENV=docker（Docker/Daytona）。
  • 两个例外：硬核黑名单（rm -rf /、fork bomb）容器内仍不跳过；绑定宿主机路径（MOUNT_CWD_TO_WORKSPACE=true）时 Docker 停止跳过。

3.2 记忆系统深挖（专项研究，9 条 3-0）

M1双文件冻结快照 3-0

~/.hermes/memories/ 下 MEMORY.md（2,200 字符，~800 token）与 USER.md（1,375 字符，~500 token），字符上限经 memory.memory_char_limit / user_char_limit 可配。源码 tools/memory_tool.py:165 精确一致。字符计数是"模型无关"的设计选择。

M2冻结快照 = 缓存保护 3-0

快照在会话开始捕获一次，中途永不改写系统提示词——故意保护 LLM 前缀缓存。中途写入即时落盘但不进提示词，直到下个会话（或上下文压缩重建）；工具响应始终显示实时状态。源码：agent/system_prompt.py 缓存提示词于 agent 生命周期；save_to_disk() 每次变更即原子写盘。

M3不自动合并 3-0

记忆满时 add 被拒（不截断不静默丢弃），返回错误要求同一回合内用 replace 合并 / remove 删旧再重试。文档建议 80% 容量即合并。每回合最多失败 3 次（_MAX_CONSOLIDATION_FAILURES_PER_TURN=3）后终止"save skipped"。

错误原文："Consolidate now: use replace to merge overlapping entries into shorter ones or remove stale or less important entries..., then retry this add — all in this turn."

M4可插拔 provider 3-0

内置记忆始终叠加激活，外置 provider 恰好 8 个：Honcho、OpenViking、Mem0、Hindsight、Holographic、RetainDB、ByteRover、Supermemory。同时最多一个（memory.provider 配置），防工具 schema 膨胀与后端冲突。

M5每回合生命周期 3-0

外置 provider：每次 API 调用前 prefetch() 快速后台召回；每回合后 sync_turn() 非阻塞持久化，跑在单后台 worker（max_workers=1）上串行——慢 provider 永不卡住回合。内置记忆两者皆 no-op（全靠冻结快照 + memory 工具）。

M6系统提示词三层结构 3-0

内置记忆快照、用户画像快照、外置 provider 块、时间戳/会话/模型行都坐在系统提示词的volatile 层——但仍是"每次会话构建一次、全回合复用"的缓存提示词，不是逐回合临时注入。

M7mem0 插件 3-0

  • 三连接模式：Platform（api.mem0.ai 托管云，默认，需 MEM0_API_KEY）、Self-hosted（Docker 跑 Mem0 server，HTTP + X-API-Key）、OSS（进程内 mem0ai，自带 LLM/embedder/vector store）。
  • 恰好四工具：mem0_search / mem0_add / mem0_update / mem0_delete。
  • mem0_add 原样存事实（infer=False）；LLM 语义抽取由 sync_turn 回调用 infer=True 单独完成。

四、OpenClaw — 对比基线

OpenClaw 是个人 AI 助手类 harness 的成熟基线：多平台网关（Telegram/Discord/Slack/WhatsApp/Signal 等），配置体系含 SOUL.md / AGENTS.md / MEMORY.md，有子代理能力。其 PR #53212（拆分系统提示词静态/动态块以保缓存前缀）与 Hermes 的缓存经济学形成互证。

关键事实：Hermes 官方提供 《Migrate from OpenClaw》指南——hermes claw migrate 直接导入 ~/.openclaw/ 的 SOUL.md/AGENTS.md/MEMORY.md。这是本报告中最硬的"两项目关系"证据：OpenClaw 是 Hermes 的迁移源，Hermes 是 OpenClaw 的迁移目标。

注意：OpenClaw 在本轮四份研究中的独立 claim 验证较少（主要作为对比基线出现）。其平台数、记忆细节此前报告已有覆盖，未重复验证。

五、OpenHuman — 架构深挖

GPL-3.0 · ~36k stars · 早期 beta · 本地优先 · 23 条确认 / 2 条证伪

5.1 核心：tinyagents 2.1 图引擎

A1Graphs, not loops 18-0 最强证据

每个 agent 回合、子代理委派、保存的工作流都编译为检查点状态机图：可暂停等人工（HITL）、可跨重启恢复、精确续跑。旧自研 run_turn_engine 已删除，三入口（Agent::turn、channel/CLI 总线、run_subagent）统一走 run_turn_via_tinyagents_shared。无进展断路器（identical-call 阈值=3）。

A2多代理编排原语 6-0

graph::parallel::map_reduce 扇出 + spawn_parallel_graph 脚手架 + TaskStore 生命周期；委派流程 plan → execute ⇄ review → finalize CompiledGraph，用条件路由、RecursionPolicy、FileCheckpointer、CancellationToken、GraphTracingSink。⚠️ 迁移部分进行中（issue #4249），持久检查点适配器状态未完全解决。

5.2 Memory Tree

A3确定性桶密封管道 11-1

源 → 规范化 Markdown → ≤3k-token 分块 → 评分（信号+嵌入+实体抽取）→ 折叠进 per-source/per-topic/per-day 树。存 SQLite（<workspace>/memory_tree/chunks.db）+ 可编辑 .md 于 wiki/，镜像为 Obsidian vault——"不是向量汤黑盒"。

"tree::bucket_seal appends the leaf to the open bucket at L0. If the bucket fills, it seals: summarise.rs produces the L1 summary, which becomes a leaf in the L1 bucket, and the cascade continues upward until a non-full bucket is hit."

3-0 Global/Topic 派生树已删除（不含原创内容），只保留 Source 树 + 实体索引。

A4读源 + 写目标 3-0

回合前记忆加载器注入相关 chunk（带引用溯源）；回合后 archivist 蒸馏长期事实 + 情节索引，后台 tokio::spawn 写回为新 chunk。

5.3 编排与安全

A520 分钟自动抓取 13-2

全局定时器 TICK_SECONDS=1200，每 tick 遍历活动集成，按各自间隔调 provider.sync(SyncReason::Periodic)，新数据走与手动相同的 ingest 管道。⚠️ 文档说"每 20 分钟"，但代码默认 sync_interval_secs=24h——实际每连接节奏可能慢得多。

A6Signal E2E 编排 Signal 部分 6-0 / x402 部分 2-1

tiny.place 会话用 Signal 协议（X3DH + Double Ratchet）真端到端加密；身份密钥设备端生成、永不落盘；配对基于同意（pending→linked→blocked）且 fails-closed（未配对的 agent 消息只当"消息"不当"指令"）。x402 支付（USDC）仅 vendor 声称，未独立审计。

A7分裂脑常开架构 3-0

快速反射 agent（秒级分诊，可用 gemma3:1b 这种小模型）→ 深度推理核心 → "潜意识" Deep Reflection Layer 以 20:1 压缩回顾会话历史并注入 STEERING_DIRECTIVE，使周级会话保持有界。

六、holaOS — 架构与定位

Modified Apache 2.0 · ~5.5k stars / 397 forks · 本地优先 TypeScript/Electron · 23 条确认 / 2 条证伪

H1定位：工作区层，非执行器 3-0

同一工作区并排跑 Claude Code / Codex / 自研 holaOS agent，共享记忆、工具、MCP 服务器、技能、应用（agent-agnostic，无锁定）。竞争对象是 agent SDK（Cline SDK、Anthropic Agent SDK、OpenAI Agent SDK），而非执行器。每个 workspace 是长期运行的 AI 环境，跨会话携带记忆/应用/文件/输出/自动化。

H2架构 3-0

TypeScript monorepo（Node 24.14.1，bun/turbo）：desktop（Electron ^41.2.0）、runtime（harness-host、state-store、api-server）、sdk（app-sdk）。MCP 一等公民——runtime 作为 MCP 客户端发现并绑定本地/远程工具服务器。运行时打包为平台特定 bundle 从 GitHub Releases 拉取。

H3单一共享 markdown 记忆 3-0（代码级验证）

文件系统后备、纯 markdown、人类可读可编辑、本地优先不云锁。实现：turn-memory-writeback.ts 写 identity/*.md、preference/*.md、workspace/<id>/knowledge/{procedures,blockers,reference,facts}/*.md；memory-recall-manifest.ts 解析 YAML frontmatter；SQLite embedding 索引只是派生层。memory_retrieve/remember 工具暴露给外部 harness（Claude Code/Codex）共用同一记忆。

H4Workspace 模型 3-0

每 workspace 自包含：自己的 agent 身份、跨会话记忆、已装平台应用（Gmail/LinkedIn/Reddit/GitHub/Google Sheets）、markdown skills（共享 house-style 指令）、定时/事件自动化。workspaces 不共享状态。Beta 0.1（2026-05，macOS）三大支柱：Multi Workspaces / Sub Agents / Dashboards。

重要 caveat：holaOS 与 Hermes/OpenClaw/OpenHuman 的直接对比 claims 均未通过 3 票验证（各 1-2 被证伪）。只有它自己的定位（工作区层 vs agent SDK）存活。请勿把四者间的竞争关系当既定事实。另：ninjahawk/hollow-agentOS 是无关项目（消费硬件自修改系统，~291 stars），勿混淆。

八、验证方法与边界

  • 方法：每轮 5-6 个搜索角度 → 抓取 17-22 个来源 → 提取 80-105 条 falsifiable claims → 3 票对抗验证（2/3 票证伪即杀）→ 合成去重后按置信排序。
  • 规模：4 轮共 405 个研究代理、3,882 次工具调用、~644 万 token。确认 95 条、证伪 5 条、0 条未验证。
  • 时间性：全部验证于 2026-08-05 的 live main 分支；项目活跃演进，具体数字（stars、版本）会漂移。
  • 依赖来源：OpenHuman 与 holaOS 的 claims 主要来自项目自己的文档/源码（描述性架构 claim 的合理来源），但 OpenHuman"早期 beta"、无独立安全审计；holaOS 基准为厂商自述。
  • 未覆盖：无独立 hands-on 实测；holaOS 与前三者的对比关系未能验证；OpenHuman 的持久检查点迁移状态未解决。
